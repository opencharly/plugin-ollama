# 2026.289.0014 — fix(ollama): adapt to ollama 0.40 - Copy now returns a progress response

## Summary

`candy/plugin-ollama` does not build against a current workspace, and that failure stops `charly` itself
from building. This fixes it: one pin bump, one line of code.

Upstream `github.com/ollama/ollama` changed **exactly one** of the twelve methods this plugin calls
between the pinned `v0.32.14` and the resolvable `v0.40.5`:

| version | signature |
|---|---|
| `v0.32.14` (was pinned) | `func (c *Client) Copy(ctx context.Context, req *CopyRequest) error` |
| `v0.40.5` (now pinned) | `func (c *Client) Copy(ctx context.Context, req *CopyRequest) (*ProgressResponse, error)` |

so any workspace resolving a newer `ollama` failed outright:

```
candy/plugin-ollama/command.go:304:12: assignment mismatch: 1 variable but client.Copy returns 2 values
```

`cmdCopy` now discards the new response. The CLI's own `copied <src> to <dst>` line is its completion
signal and `Copy`'s progress stream was never consumed here, so the return is genuinely unused rather than
swallowed.

**Scope measured rather than assumed, twice.** All twelve upstream methods this plugin calls were compared
between the two versions: exactly ONE changed signature, so no other call site moves. And all 63 welded
internal modules were each built individually — **62 build, and this is the only one that does not**. That
second measurement corrects `opencharly/charly#886`'s own framing: the remedy is one producer release, not
a wave across 66 modules.
